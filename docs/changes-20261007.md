## 规则预抽元数据 v3（`source_metadata.py`）

- 文件自身身份（发布机关、本文文号、发布日期）只取自身声明，依次为：
  - 标题；
  - 规则库或法规库的元数据表（文号、发文单位、发文日期）；
  - 页首发布记录，如“（某年某月某日某令第N号公布，自某日起施行）”；
  - 独立成行的页首或落款。
- 网页页脚（版权所有、ICP备案）和正文中的引用句不再算作发布机关；紧跟在被引文件标题后的括注视为引用，不算本文记录。全角数字与括号的文号可识别。
- 发布机关：
  - 联合发文取标题中最先出现的机关；
  - 中债资信与中央结算分开；
  - 标题未写明机关时，按本文文号前缀认定。
- 层级：
  - 新增“行政法规”和“财税规范性文件”；
  - 无发布机关的“证券投资基金……指引/规定/决定/通知”归入证监会规范性文件；
  - 估值、核算、操作细则、工作指引类归入行业自律规则；
  - SOP或笔记类内部资料归入实务手册与案例。
- 日期：
  - 修订版的“自发布之日起施行”不借用废止条款里旧版的发布日期；
  - “审议通过”日期不当作发布日期；
  - “自某日起停止执行”不当作施行日期。
- 关联：
  - “发布”只认本文自身的声明（“现公布《…》”“关于发布《…》的通知”），历史叙述句不算；
  - 同一文件的不同版本不互相“发布”；附件不算发布通知本身；
  - “除……外”中的文件不算被废止；“《通知》中附件N《…》”只认附件；
  - 后接条款号或引文的标为部分条款废止或停止执行（新链接类型 `partially_abolishes` / `partially_abolished_by`）；
  - 无版本号的同名文件按施行或落款年份排出新旧版本。
- 预抽结果仍只是线索：绑定版本内容哈希，不修改 `legal_status`、`valid_from` 或关系边，不替代管理员登记的效力事实，不调用模型。
- 版本号变化后，旧候选按设计不再加载。升级后须对每个空间运行一次 `scripts/extract-source-metadata.py --apply`；导入或发布新来源后也应重新运行。

## 库地图 v3（`library_map.py`）

每份来源新增“文号”（仅限能可靠识别的本文文号），并区分“部分条款被废止或停止执行”。层级顺序加入行政法规与财税规范性文件。

## 知识页状态措辞

- 答疑读取知识页时跳过 `warning` 类型的平台提示块，如“模型生成修订候选，尚未核验……”“本地迁移待核验 Wiki……”。这些提示是创建时的状态说明，页面状态已在页头单独给出；它们不再被读入答疑上下文，也不再分配可引用编号。页面显示不变。
- 编译规范 `wiki-compilation/1.3`：
  - 来源的 `review_notice`（资料分类、审核状态、效力字段、归档标注）只用于识别历史版本或征求意见稿，不写进页面标题或正文；
  - 施行、废止与新旧替代只依据来源原文自身的条款；
  - 来源不足时写明缺少哪份原文或规定，不写泛泛的“待核验”。

## 规划期间预取原问题检索

推理核心的计划检索总以原问题为第一条。现在在模型规划时，用后台线程以同一批量检索函数和输入先检索原问题；规划结束后只检索规划新增的查询，再按原顺序合并（`universal_retrieval.search_many_catalog(prefetched=...)`）。候选池、重排与合并规则不变；预取失败或任务取消时照常重新检索。回执记 `prefetched`（查询数、配对数、与规划重叠的耗时）；计时新增 `retrieval_prefetch_overlapped`，与规划重叠，不计入串行时间。

同期试验未采用：

- 缩小每条查询的重排候选数：80 改为 48 时，前 16 个检索单元只有约 84% 相同；
- 加大重排批量：长文本反而更慢。

## 追加：财政部会计规定的标题写法（`source_metadata.py`）

规则预抽的层级判断原先只认“……会计处理规定”。财政部会计规定也常写成“……会计处理的规定”（如《永续债相关会计处理的规定》）或“……会计处理暂行规定”。附件形式发布的规定正文里通常没有发布机关和文号，此前会落入“其他来源”。现三种写法都归入“会计准则及财政部会计规定”，测试补了两条断言。

只是补认标题写法，预抽版本号 `source-metadata-rules-v3-20261007` 不变。在一个实际资料库上逐项比对，原有来源的预抽结果没有任何变化，无需重新运行预抽；新导入的来源照常运行 `scripts/extract-source-metadata.py --apply`。
